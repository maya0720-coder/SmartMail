# 제안된 업무 — 컨셉 재기획안

> 대상: SmartMail '제안된 업무' 화면(TODO-01·02, 기획서 6장)
> 작성일: 2026-11-13 · 상태: 제안(사용자 선택 전)
> 시안: `designMD/04_제안된업무_시안/index.html`(A·B·C 3종 비교, 가상 데이터)

## 1. Agenda — 왜 바꾸나

### 1-1. 현재 화면 진단 (데모 모드 확인)

| 문제 | 현재 모습 | 사용자에게 생기는 일 |
|---|---|---|
| 결정할 근거가 부족 | 표 한 줄에 제목 입력칸 + 근거 한 문장(회색, 2줄 잘림) | 메일을 열어 봐야 판단할 수 있어 결국 아웃룩으로 돌아감 |
| 제목이 맥락을 잃음 | "확인 부탁드립니다." 같은 요약 제목, 원래 메일 제목은 안 보임 | 무슨 일인지 알아볼 수 없음 |
| 모든 칸이 입력칸 | 제목·구분·기한이 처음부터 편집 상태 | 화면이 무겁고, '고칠 것'과 '판단할 것'이 구분되지 않음 |
| 결정지가 둘뿐 | 승인 / 무시 | '지금은 아니지만 할 일'을 둘 곳이 없어 무시하거나 억지로 승인 |
| 우선순위가 없음 | 수집 순서대로 나열, 전자결재와 일반업무가 섞임 | 급한 요청이 묻힘 |
| 목적과 끊김 | 승인하면 목록에서 사라질 뿐 | 이 승인이 주간보고에 어떻게 들어가는지 보이지 않음 |
| 기획서와 차이 | 기획서 6장 '추출 근거(문장 하이라이트)'가 메일 맥락 없이 문장만 표시 | C5(점검 결과)와 같은 문제 |

### 1-2. 이 화면의 본래 역할

> **"메일함에서 '내가 해야 할 일'만 빠르게 골라내는 곳"**
>
> 판단(이게 내 일인가?)이 먼저고, 편집(제목·기한 다듬기)은 필요할 때만 한다.

## 2. MECE — 설계 원칙 5가지

| # | 원칙 | 구체적으로 |
|---|---|---|
| 1 | 근거 먼저 | 요청 문장을 메일 맥락 안에서 하이라이트하고, '왜 제안됐는지'(요청 표현·기한 표현·받는 사람·스레드)를 칩으로 보여준다 |
| 2 | 결정지 3개 | **할 일로** / **나중에**(다시 제안) / **업무 아님**(비슷한 메일은 덜 제안) |
| 3 | 편집은 필요할 때만 | 제목·구분·기한은 평소 읽기 모드, 클릭하거나 E 키를 눌렀을 때 편집 |
| 4 | 우선순위와 묶음 | 오늘·어제·이번 주로 묶고, 기한·확신도를 표시. 전자결재는 따로 모아 '결재함 열기'로 연결 |
| 5 | 목적과 연결 | 승인할 때 '주간보고 예상 위치'(금주 실적·차주 계획·이슈)를 보여주고, 필요하면 바꾼다 |

## 3. Hypothesis — 컨셉 3안

| 구분 | A. 트리아지(받은편지함형) | B. 포커스 카드(한 장씩 결정) | C. 분류 보드(주간보고 연결형) |
|---|---|---|---|
| 한 줄 설명 | 왼쪽 목록 + 오른쪽 근거 메일, 키보드로 빠르게 결정 | 카드 한 장씩 보고 끌어서 결정 | 정리 전 → 이번 주(실적·계획·이슈) / 나중에 / 업무 아님 칸으로 끌기 |
| 참고 패턴 | 메일 클라이언트 트리아지, 지원 티켓 큐 | 카드 스와이프 | 칸반 |
| 좋은 점 | 양이 많아도 빠름. 기획서 '근거 하이라이트'에 가장 가까움. 키보드만으로 처리(A·S·D·E) | 결정 피로가 적고 직관적. 좁은 화면에 강함 | 승인 순간 주간보고 칸이 정해져 앱 목적과 바로 연결. 한 주를 한눈에 봄 |
| 아쉬운 점 | 처음 보는 사람에겐 정보가 많아 보일 수 있음 | 건수가 많으면 느림. 여러 건 비교가 어려움 | 끌기 조작이 번거롭고, 대시보드와 역할이 겹침 |
| 적합한 상황 | 매일 10~30건 | 아침 첫 정리, 5~10건 | 주간보고 쓰기 직전 |
| 구현 난이도 | 중 | 중 | 중상(끌어 놓기 접근성 대안 필요) |

### 5-2. 데이터·도메인 변경 (결정기록 필요)

| 항목 | 내용 | 영향 |
|---|---|---|
| '나중에' 상태 | `Task.snooze_until`(날짜) 추가. 상태는 '제안됨' 유지, 목록에서는 그 날짜까지 숨김(기본: 다음 근무일 아침) | 상태 전이 표(TODO-03) 변경 없음. 저장 필드 1개 추가 |
| 제안 이유 | 추출 단계에서 판단 근거를 `reasons`(최대 4개 코드: 요청 표현·기한 표현·단독 수신·회신 대기·결재 키워드·참조 수신)로 저장 | 메일 원문 저장 아님(코드·짧은 라벨만) → MAIL-08 유지 |
| 확신도 | AI 분류 확신도(이미 프롬프트에서 받음)를 `confidence`로 저장, 0.7 미만은 '확신도 낮음' 탭 | AI 실패 시 규칙 기반 값(요청 표현 개수 등)으로 대체 |
| '업무 아님' 학습 | 무시한 메일의 보낸 사람·제목 말머리를 **로컬 규칙**으로 누적 → 다음 수집 때 확신도 감점(자동 제외는 하지 않음) | 개인 PC 로컬에만 저장, 설정에서 초기화 가능 |
| 주간보고 예상 위치 | 기한·상태로 계산(이번 주 완료 예정 → 금주 실적, 다음 주 기한 → 차주 계획, 지연·오류 문의 → 이슈), 사용자가 바꾸면 업무에 저장 | WIKI-01 분류에 사용자 지정 우선 적용 |
| 근거 하이라이트 | 상세를 열 때 원본 메일을 다시 읽어(메모리) 요청 문장 위치를 표시. 원본이 없으면 '원문 없음'(MAIL-09) | 저장 없음 |
| 제목 규칙 | 업무 제목 = **대상 + 행동**(예: "KSB1 조회 권한 부여"). 일반 문구("확인 부탁" 등)만 남으면 메일 제목 유지. 원래 메일 제목은 항상 함께 표시 | 점검 결과 D1과 같은 조치 |

### 5-3. 단계별 진행

| 단계 | 범위 | 완료 기준 |
|---|---|---|

| 2 | 오늘·어제·이번 주 묶음, 전자결재·확신도 낮음 탭, 진행 막대, 주간보고 예상 위치 | WIKI-01 초안에 사용자 지정 위치가 반영됨 |
| 3 | 빠른 정리 모드(B안), '업무 아님' 로컬 학습과 초기화 | 학습 규칙이 로컬에만 저장되고 초기화되는지 테스트 |

### 5-4. 지켜야 할 제약(현재 코드 기준)

- CSP·외부 리소스·`innerHTML` 금지 규칙을 따른다. 시안 HTML은 설명용이라 `innerHTML`을 썼지만, 실제 구현은 `el()`로만 그린다.
- 근거 문장·메일 본문은 저장하지 않는다(MAIL-08). 이유 칩은 코드값만 저장한다.
- 끌기 조작(B·C안)에는 버튼·키보드 대안을 항상 함께 둔다(접근성).
