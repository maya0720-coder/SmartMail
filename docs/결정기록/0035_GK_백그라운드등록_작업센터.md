# 0035 G-Knowledge 백그라운드 등록·작업 센터

- 날짜: 2026-11-17
- 상태: 구현 완료(가짜 G-Knowledge로 검증). 실제 사이트에서 백그라운드 등록 1회 점검 필요
- 관련 요구사항: GK-03·04·06, 결정기록 0008·0032
- 근거 문서: `수정사항_20261117020320.md` N2·U1(사용자 승인 2026-11-17)

## 배경

- `POST /api/gk/register`가 브라우저 자동화를 바로 실행했다. 화면 열기, AI 분석(최대 60초), 등록요청, 접수 확인까지 끝날 때까지(최대 150초) HTTP 응답과 등록 모달이 묶였다.
- 등록 결과는 '검토 대기(REVIEW)'로 접수된다(0032). 따라서 '등록 완료(검토 대기)'가 정확한 문구다.

## 결정

1. **즉시 접수(202)**
   - 등록 API는 입력을 검증하고 재마스킹한 뒤 큐에 넣는다. 응답은 바로 `202 {state:"queued"}`다.
   - 모달은 곧바로 닫히고, 토스트로 "등록을 시작했습니다 · 진행은 작업 센터에서 확인"을 띄운다.
2. **업무별 상태(`task.gk_state`, 스키마 5)**
   - 상태 흐름: `queued → running(단계 open·analyze·submit) → requested | failed_unsent | unknown`
   - 사유는 코드 값만 저장한다(`gk_state_reason`, 영문 소문자·밑줄 32자, DB CHECK).
   - `failed_unsent`(등록요청 **전** 실패): 로그인 필요, 필드 미설정, 바쁨, 본문 확인 실패, 분석 시간 초과. 다시 시도해도 중복 등록이 생기지 않는다.
   - `unknown`(등록요청 **뒤** 결과 미확인): 자동 재시도하지 않는다. 화면에 `[등록됨으로 표시]`와 `[다시 시도]`를 둔다.
     - `[다시 시도]`는 중복 경고를 확인받는다. 서버는 `retry_unknown` 없이 다시 보내면 409(`confirm_required`)로 거부한다.
3. **어댑터 예외 구분**
   - `RegisterNotSentError(code)`와 `RegisterResultUnknownError`를 추가했다. 둘 다 `KnowledgeUnavailableError`의 하위 클래스라 기존 처리와 호환된다.
   - 브라우저 어댑터는 등록요청 클릭 전·후로 구분해 이 예외를 낸다. 단계 콜백(`on_step`)으로 진행 단계를 알린다.
4. **큐(`app/gk_job.py`)**
   - 처리는 1건씩 한다(브라우저 실행기 1개). 사용자가 누른 작업만 처리하므로 백그라운드 작업 설정과 관계없이 항상 켠다.
   - 큐에는 **마스킹된 초안만** 메모리에 둔다. 앱을 끄면 사라지고, DB에는 상태 코드만 남는다.
   - 앱 시작 시 남은 `queued`와 `running`(open·analyze 단계)은 `failed_unsent(app_restart)`로 바꾼다. `running(submit)`은 등록됐을 수 있으므로 `unknown(app_restart)`로 바꾼다.
   - 중복 방지는 그대로 쓴다: 이미 등록됨, 같은 업무 진행 중(409), 같은 제목 검사.
5. **상태 조회**
   - `GET /api/gk/status?ids=…`(숫자만, 최대 100개)와 업무 응답의 `gk_state`로 조회한다.
   - 화면은 작업 센터 폴링으로 갱신한다: 진행 중이면 3초, 없으면 20초 간격이고, 숨긴 탭에서는 멈춘다.
   - 상태가 바뀌면 열린 상세를 다시 그린다.
6. **작업 센터(U1)**
   - 상단 바의 연결 칩 옆에 작업 버튼과 진행 중 건수 배지를 둔다. 실패가 있으면 버튼 테두리를 강조한다.
   - 서버 `GET /api/jobs`는 각 작업이 메모리에 가진 상태만 합친다. 새로 저장하는 것은 없다.
     - G-Knowledge 등록(최근 50건, 마스킹된 제목)
     - AI 요청 요약(진행률·대기·로그인 필요)
     - 메일 수집(진행 중·마지막 수집)
     - 회사명 조회(진행 중·최근 확인 건수)
     - 위키 양식 읽기는 5단계(0037)에서 연결한다.
   - 줄마다 작업 이름, 대상, 상태 문구(사유 코드 → 화면 문구), 시각, 행동 버튼(다시 시도·등록됨으로 표시·지금 요약·로그인)을 보여 준다.
   - 완료·실패로 바뀌면 토스트를 한 번 띄운다.
   - 등록 미리보기는 대시보드에만 있다. 그래서 다른 화면에서 `[다시 시도]`를 누르면 `/?gk=업무번호`로 이동해 연다.
7. **화면**
   - 상세 '지식 등록' 칸은 상태 칩을 보여 준다: 등록 대기, 등록 중·단계, 등록 완료(검토 대기), 실패·사유, 확인 필요.
   - 진행 중에는 등록 버튼을 막는다.
   - 이미 등록한 업무에는 '재등록' 버튼을 더 보이지 않는다. 중복 등록은 원래 불가능했다(GK-06).
8. **회사명 조회 작업**: 작업 센터 표시를 위해 `running`·`last_run_at`·`last_saved`만 노출했다.

## 보안·개인정보

- 큐와 작업 센터에는 마스킹된 초안·제목만 메모리에 둔다. DB에는 상태·시각·사유 코드만 저장한다.
- 테스트로 확인했다: 합성 주민등록번호를 본문에 넣어도 DB 전체와 로그에 남지 않는다.
- 상태 API는 숫자 목록만 받는다(형식·개수 제한). 표시 동작(`mark-registered`)은 CSRF 검사 대상이고, `unknown` 상태에서만 허용한다.

## 남은 확인

- 실제 사이트에서 백그라운드 등록 1회와 단계 문구를 확인해야 한다.
- AI-Ground 요약과 같은 브라우저 실행기를 함께 쓸 때 대기열 시간 초과가 없는지 확인해야 한다. 필요하면 형제 실행기(0026)로 옮긴다(지시서 7장).
