# 0005. 04단계 자격증명 처리 방식과 03·04단계 보안 검토 반영

- 날짜: 2026-11-11
- 단계: 03·04(05 진행 중 반영)
- 상태: 적용

## 자격증명 처리 방식

- 로그인 API는 JSON 본문만 받습니다. 받은 값은 곧바로 `bytearray`로 옮기고, 어댑터 호출이 끝나면 성공·실패와 관계없이 0으로 덮어씁니다.
- **남는 한계:** JSON을 파싱할 때 Python `str`(불변 객체)이 잠시 생깁니다. 이 값은 덮어쓸 수 없어 참조를 바로 끊고 GC에 맡깁니다. 디스크·로그·DB에는 남지 않으며, 이는 AUTH-10 테스트로 검증합니다.
- 실제 사이트의 ID·암호 로그인 어댑터는 사이트별 로그인 규격을 확인한 뒤 추가합니다(확인 필요). 그 전에는 다음과 같이 동작합니다.
  - 일반 모드: `503 연동 규격 확인 필요`를 돌려줍니다.
  - 데모 모드: 가짜 어댑터를 씁니다.
- 2단계 인증·SSO 사이트는 `SMARTMAIL_BROWSER_LOGIN_SITES`에 지정합니다. 지정한 사이트는 브라우저 창에서 사용자가 직접 로그인하고, 앱은 입력값을 받지 않습니다(AUTH-09). 로그인 완료 판정(같은 호스트로 돌아오고 주소에 'login'이 없을 때)은 실제 사이트에서 수동 점검이 필요합니다.

## 남은 위험(사용 환경 확인 필요)

- **같은 PC의 다른 사용자·프로세스:** 다른 사용자나 프로세스가 `127.0.0.1:포트`로 접속하면 화면의 CSRF 토큰을 읽을 수 있습니다. 이렇게 되는 환경은 공유 VDI, 원격 데스크톱 서버 등입니다.
  - 개인 PC에서 실행한다고 전제하고 실행 토큰 인증은 넣지 않았습니다.
  - 공유 서버에서 쓴다면 시작 URL 토큰과 HttpOnly 쿠키 방식을 추가해야 합니다(웹 배포 시 SSO로 대체).
- **같은 PC에서 앱을 두 번 실행:** 나중에 시작한 쪽의 잔존 검사가 다른 쪽의 브라우저 임시 폴더를 지울 수 있습니다. 앱은 한 번만 실행하도록 안내합니다(로컬 실행 가이드).
