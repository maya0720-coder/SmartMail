# 업무 처리 관리 현황 페이지 기획서

Nov 11, 2026 · @maya0720

## 1. Agenda Framing — 무엇을 해결하는가

결론: 업무 메일을 자동으로 할 일(To-do)로 바꾸고, 처리 결과를 위키
주간보고와 업무 히스토리로 이어지게 하는 전사 웹 페이지를 만든다.

| 구분      | 내용                                                                                 |
|-----------|--------------------------------------------------------------------------------------|
| 배경      | 업무 요청이 메일로 흩어져 누락·중복이 생기고, 주간보고를 매주 수작업으로 다시 정리함 |
| 목적 1    | PC 아웃룩 메일(필요 시 그룹웨어 메일함) → 내가 할 업무 To-do 자동 생성               |
| 목적 2    | 처리 완료/진행 업무 → 위키(Confluence) 주간보고 자동 업데이트                        |
| 목적 3    | 회신 메일 기반 업무 히스토리 축적 → 키워드 검색으로 유사 업무 가이드                 |
| 목적 4    | 업무 처리 내용 → 버튼 한 번으로 G-Knowledge(사내 지식 시스템)에 지식 등록            |
| 목적 5    | 자체 가이드가 어려우면 AI-Ground의 g-llm으로 지식 검색·피드백                        |
| 실행 환경 | 테스트 버전은 사용자 PC 로컬 실행(localhost), 최종은 사내 웹 배포                    |
| 대상      | 1단계 IE팀 로컬 테스트 → 2단계 웹 배포·전사 확대                                     |
| 범위 제외 | 메일 자동 회신·발송, 결재 처리, ID·암호 저장(자동 로그인 포함)                       |

성공 지표(제안, 파일럿에서 기준값 측정 후 확정):

- 주간보고 작성 시간 감소율

- 메일 기반 To-do 추출 정확도(사용자가 수정 없이 승인한 비율)

- 유사 업무 검색 후 '도움 됨' 응답 비율

- 주간 활성 사용자 수

## 2. MECE Questioning — 풀어야 할 질문

목적을 데이터 흐름 순서(입력 → 처리 → 출력 → 축적 → 운영)로 나눠
중복·누락 없이 질문을 정리했다.

| 영역                  | 핵심 질문                                           | 결정이 필요한 사항                                                   |
|-----------------------|-----------------------------------------------------|----------------------------------------------------------------------|
| 입력(메일 수집)       | 어느 메일을, 어떤 권한으로, 얼마나 자주 가져오는가? | 사내 메일 시스템 종류, API 접근 방식, 수집 범위(받은 메일/참조/회신) |
| 처리(업무 추출)       | 어떤 메일이 '내가 할 일'인가?                       | To-do 판별 기준, 기한·요청자·우선순위 추출 규칙, 스레드 묶음         |
| 출력(현황·주간보고)   | 무엇을 보여주고, 위키에 어떤 형식으로 쓰는가?       | 상태 체계, 주간보고 템플릿 매핑, 게시 전 사용자 검토 여부            |
| 축적(히스토리·가이드) | 회신 메일에서 무엇을 저장하고 어떻게 찾는가?        | 저장 단위(문제-해결 쌍), 키워드/의미 검색, AI 호출 조건              |
| 운영(보안·배포)       | 전사 배포 시 개인정보·보안을 어떻게 지키는가?       | 데이터 보관 위치, 외부 AI 전송 허용 범위, 권한 모델, 운영 주체       |

## 3. Hypothesis Driven Analysis — 해결 가설

아래 가설은 기획 단계의 추정이며, 파일럿에서 검증한 뒤 확정한다.

| \#  | 가설                                                                                                  | 검증 방법                                                        | 기각 시 대안                                             |
|-----|-------------------------------------------------------------------------------------------------------|------------------------------------------------------------------|----------------------------------------------------------|
| H1  | 업무 메일의 다수는 규칙(받는 사람/참조, 요청 표현, 기한 표현) + AI 분류로 To-do 여부를 식별할 수 있다 | IE팀 메일 2~4주치로 추출 결과를 사용자가 승인/수정 → 승인률 측정 | 자동 등록 대신 '추천 후 사용자 승인' 방식 유지           |
| H2  | 주간보고는 완료/진행/예정 업무 목록으로 대부분 채워진다                                               | 기존 위키 주간보고 포맷과 항목별 매핑 가능률 비교                | 초안만 자동 생성, 사용자가 편집 후 게시                  |
| H3  | 회신 메일에는 재사용 가능한 처리 방법(T-code, 원인, 조치)이 담겨 있다                                 | 회신 메일 샘플에서 '문제-원인-조치' 추출 성공률 확인             | 완료 처리 시 사용자가 요약 1줄을 직접 남기는 입력란 추가 |
| H4  | 키워드 검색만으로는 유사 업무 발견이 부족하므로 의미(임베딩) 검색을 병행해야 한다                     | 동일 질의에 대한 키워드 vs 하이브리드 검색 적중률 비교           | 키워드 + 태그(모듈·시스템) 정교화로 대체                 |
| H5  | 유사 사례 점수가 낮을 때만 AI를 호출하면 비용·보안 리스크를 통제할 수 있다                            | 호출 빈도·비용·피드백 만족도 로그 분석                           | 사용자 수동 호출만 허용                                  |

## 4. 기능 요구사항

필수(M)는 1단계 파일럿에 포함, 권장(S)은 2단계, 선택(C)은 후속 검토
대상이다.

### 4.1 메일 수집

| ID      | 요구사항                                                                                                                                  | 우선 |
|---------|-------------------------------------------------------------------------------------------------------------------------------------------|------|
| MAIL-01 | 접속한 PC에 설치된 아웃룩(클래식)의 메일을 로컬에서 읽음                                                                                  | M    |
| MAIL-02 | 새 아웃룩 등 아웃룩으로 읽을 수 없는 PC는 그룹웨어 메일함으로 전환해 수집(로그인 창 경유)                                                 | M    |
| MAIL-03 | 받은편지함 + 보낸편지함(회신) 수집, 스레드(대화) 단위로 묶음                                                                              | M    |
| MAIL-04 | 기간 지정 수집(기본: 주간보고 주기) + 수동 새로고침                                                                                       | M    |
| MAIL-05 | 제외 규칙: 공지·뉴스레터·자동발송·특정 발신자/폴더 제외                                                                                   | M    |
| MAIL-06 | 첨부파일은 읽지 않고 파일명만 표시                                                                                                        | S    |
| MAIL-07 | 사용 중인 아웃룩 종류(클래식/새 아웃룩) 자동 감지 후 수집 경로 자동 선택                                                                  | M    |
| MAIL-08 | 메일 원문은 저장하지 않음. 메일 참조 ID(예: 아웃룩 EntryID, Internet Message-ID)만 저장하고, 볼 때마다 아웃룩·그룹웨어 원본에서 읽어 표시 | M    |
| MAIL-09 | 원본이 삭제·이동돼 찾을 수 없으면 '원문 없음' 표시, 업무·요약은 유지                                                                      | M    |
| MAIL-10 | '아웃룩에서 열기' 버튼으로 원본 메일 바로 열기(클래식 아웃룩)                                                                             | S    |

| RET-03  | G-Knowledge 등록 시 R&R 항목 포함: 업무명, 담당자, 요청 부서, 처리일, 관련 시스템·모듈, 처리 방법            | M    |

### 4.9 성과 지표(대시보드 표시)

성과 지표는 완료 건수, 기한 준수율, 지식 등록률, 이력 재사용률 4개만
둔다. 별도 메뉴 없이 대시보드 상단에 기간 선택과 함께 카드·그래프로
표시하며, 모두 시스템 기록으로 자동 계산한다(사람이 입력하는 점수 없음).

| 지표          | 산식                                            | 좋은 방향                | 데이터 출처                               | 그래프         |
|---------------|-------------------------------------------------|--------------------------|-------------------------------------------|----------------|
| 완료 건수     | 기간 내 완료 확정 업무 수                       | 참고(많을수록 처리량 큼) | 완료 확정 이벤트                          | 막대           |
| 기한 준수율   | 기한 내 완료 ÷ 기한이 있는 완료 업무            | 높을수록                 | 기한(메일 추출 후 사용자 확정), 완료 시각 | 선 + 목표 점선 |
| 지식 등록률   | G-Knowledge에 등록된 완료 업무 ÷ 완료 업무      | 높을수록                 | G-Knowledge 등록 결과(GK-06)              | 선             |
| 이력 재사용률 | 앱·G-Knowledge에서 해결된 검색 ÷ 유사 업무 검색 | 높을수록                 | 검색 해결 단계(SRCH-01~03)                | 선             |

지표 산출 방법(추천)

1.  이벤트 기록: 완료 확정, 기한 확정, G-Knowledge 등록, 유사 검색과
    해결 단계(앱/G-Knowledge/AI/미해결)를 발생 시각과 함께 자동
    기록한다. 사람이 수치를 직접 입력하지 않는다.

2.  지표 원장: 업무가 완료되면 업무 1건을 숫자 1행으로 저장한다(완료일,
    담당자, 기한 유무·준수, G-Knowledge 등록 여부, 검색 해결 단계). 메일
    제목·본문·상대방 정보는 넣지 않는다.

3.  기간 집계: 주(목~수, 주간보고 주기), 월, 분기, 반기(1~6월/7~12월),
    연(달력)으로 묶는다. 비율은 주별 비율을 평균 내지 않고 기간 전체의
    분자·분모를 합쳐서 계산한다.

4.  산식 규칙: 기한 없는 업무는 기한 준수율 분모에서, 유사 검색을 하지
    않은 업무는 재사용률 분모에서 뺀다. 모든 그래프에 표본 건수를
    표시하고, 5건 미만은 '참고'로 표시한다.

5.  비교: 지표 카드는 '최근 완료 기간 vs 직전 기간'으로 비교하고
    '개선/악화'를 글자로 표시한다. 진행 중인 기간은 그래프에 흐리게 보여
    부분 집계가 악화로 오해되지 않게 한다.

6.  목표: 도입 초기 4주 값을 기준값으로 삼고 IE팀이 목표를
    확정한다(샘플의 기한 준수율 90%는 예시).

대시보드 표시 방식

| 요소           | 표현                                                               | 비고                                |
|----------------|--------------------------------------------------------------------|-------------------------------------|
| 기간 선택      | 대시보드 우측 상단 연간 / 반기 / 분기 / 월 / 주 버튼               | 표시 기간 수: 3 / 6 / 8 / 13 / 13   |
| 지표 카드 4개  | 값 + 직전 대비 증감 + 추이 그래프 한 카드에                        | 대시보드 첫 줄, 최근 완료 기간 기준 |
| 추이 그래프    | 완료 건수는 막대, 나머지 3개는 선(기한 준수율은 목표 점선)         | 진행 중 기간은 흐리게               |
| 마우스 오버    | 기간별 값·표본 건수 툴팁                                           |                                     |
| 표로 보기      | 기간 × 지표 표(접기/펼치기)                                        | 인쇄·색 구분이 어려운 경우          |
| 업무 상태 건수 | 제안됨·진행 중·완료 후보·기한 임박은 할 일 목록 필터에 건수로 표시 | 기존 상태 KPI 카드 대체             |

주의: 이 지표는 업무 난이도 차이를 반영하지 않는다. 개인 화면은 본인만
보고, 팀·개인 간 비교 화면은 인사 평가 활용 여부를 정한 뒤 만든다.
