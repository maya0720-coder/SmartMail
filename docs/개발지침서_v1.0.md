# 개발 지침서

이 탭은 저장소 루트의 CLAUDE.md로 그대로 옮겨 쓴다. 요구사항의 원본은 기획서 탭이며, 코드는 기획서의 요구사항 ID(MAIL-01, AUTH-03 등)를 기준으로 만든다.

## 0. 작업 환경 기본 설정

- 소스 코드를 제외한 설명 문구와 md 문서는 한글로 작성한다.
- Claude Code의 피드백(진행 상황, 질문, 최종 보고)은 한글로 표시한다.
- AXHub AI 활용 기록을 켜고 작업한다. 설정 방법은 사내 AXHub 안내에 따른다(확인 필요).

## 0-1. 하네스 구조와 개발 방향

하네스 방식으로 구조 폴더를 자동 생성하고, 코딩 시 파일을 각 성격에 맞는 폴더로 분류해 생성한다. 테스트 버전은 로컬 실행이며, 이후 IE팀 운영의 사내 웹 배포로 옮길 수 있게 화면·업무 규칙·연동을 분리한다.

```text
mail-work-status/
├─ CLAUDE.md                # 이 지침서
├─ .claude/
│  ├─ settings.json         # 권한·훅 설정
│  ├─ agents/               # 보안 검토·테스트 작성·기획 대조 서브에이전트
│  ├─ commands/             # 반복 명령(점검, 보안 검토 등)
│  └─ hooks/                # 시크릿 탐지·포맷 자동 실행
├─ docs/
│  ├─ 기획서.md
│  ├─ 요구사항추적표.md
│  ├─ 결정기록/
│  └─ 변경이력.md
├─ src/
│  ├─ app/                  # 화면·API 라우터, 정적 리소스
│  ├─ domain/               # 업무·주간보고·지식·성과 지표 규칙(순수 로직)
│  ├─ collectors/           # 아웃룩(COM)·그룹웨어 메일 수집
│  ├─ integrations/         # 위키·G-Knowledge·AI-Ground 어댑터
│  ├─ security/             # 자격증명(비저장)·세션·마스킹
│  ├─ storage/              # 로컬 DB·보관기간 삭제·지표 원장
│  └─ config/               # 설정 로딩·검증
├─ tests/
│  ├─ unit/  integration/  security/
│  └─ fixtures/             # 합성 데이터만
├─ scripts/                 # 로컬 실행·점검
└─ .env.example             # placeholder만
```

하네스 규칙

1. 작업을 시작할 때 위 폴더가 없으면 이 구조대로 만든다. 새 파일은 성격(화면·API / 업무 규칙 / 수집 / 연동 / 보안 / 저장 / 설정 / 테스트 / 문서)에 맞는 폴더에만 만들고, 어느 폴더인지 애매하면 만들기 전에 위치를 보고한다.
2. 의존 방향은 app → domain ← (collectors, integrations, storage)이다. domain은 메일·외부 사이트·DB를 직접 호출하지 않고 인터페이스만 쓴다.
3. 아웃룩·그룹웨어·위키·G-Knowledge·AI-Ground 연동은 collectors/·integrations/의 어댑터로만 하고, 어댑터마다 테스트용 가짜(Fake) 구현을 둔다. 테스트는 실제 사이트에 접속하지 않는다.
4. ID·암호는 security/의 자격증명 모듈만 다루고, 로그인 1회 후 메모리에서 즉시 폐기한다. 다른 모듈은 세션 핸들만 받는다. 브라우저 자동화는 비저장 프로필로만 실행한다(기획서 4.7).
5. 위키·G-Knowledge·g-llm으로 보내는 데이터는 security/의 마스킹을 반드시 거친다. 전송 함수는 마스킹을 거친 타입만 인자로 받게 만들어 누락을 코드로 막는다.
6. 메일 원문은 저장하지 않고 참조 ID만 저장한다. 완료 후 7일 삭제는 storage/의 보관기간 작업에서 처리하고, 지표 원장 예외는 기획서 결정 후 적용한다.
7. 로컬 서버는 127.0.0.1에만 바인딩한다. 주소·포트·외부 URL은 config/와 .env로 주입하고, .env.example에는 placeholder만 둔다.
8. 기획서 요구사항 ID를 테스트 이름, 커밋 메시지, docs/요구사항추적표.md에 연결한다.
9. 작업은 계획(요구사항 ID 확인) → 구현 → 검증(포맷·린트·타입·테스트·시크릿 탐지) → 한글 보고 순서로 한다. 시크릿 탐지와 포맷은 .claude/hooks로 자동 실행한다.
10. 기획서와 다르게 판단해야 하는 경우 docs/결정기록/에 이유를 남기고 사용자 확인을 받는다.

권장 기술 스택(확정 필요): Python + FastAPI(로컬 서버), pywin32(클래식 아웃룩 COM), Playwright(G-Knowledge 등 브라우저 자동화), SQLite(로컬 DB), 서버 렌더링 HTML + JS(샘플 화면 기준), pytest·ruff·mypy.

## 개발 지침 본문

이 문서는 Claude Code가 이 저장소의 코드를 읽고, 작성하고, 수정하고, 검토할 때 따라야 하는 기본 지침이다. 저장소에 더 구체적인 지침이 있으면 함께 적용하되, 보안과 개인정보 보호 수준을 낮추지 않는다. 요구사항이 불명확하거나 위험한 변경이 필요한 경우에는 임의로 추측해 구현하지 말고, 가능한 안전한 범위까지 진행한 뒤 불확실한 점을 명시한다.

하네스 방식의 구조 폴더 자동 생성 및 코딩 시 각 성격에 맞게 분류 및 생성

### 1. 기본 원칙

- 기존 구조와 사용 기술을 먼저 확인하고, 목적을 충족하는 가장 작은 변경을 한다. 관련 없는 파일이나 동작은 수정하지 않는다.
- 읽기 쉽고 유지보수하기 쉬운 코드를 작성한다. 명확한 이름, 작은 책임 단위, 일관된 오류 처리를 사용한다.
- 입력값은 신뢰하지 않는다. 서버와 보안 경계에서 형식, 길이, 범위, 권한을 검증한다.
- 보안이나 개인정보 보호를 약화시키는 임시 우회, 비활성화, 예외 처리를 추가하지 않는다.
- 설명이나 주석만으로 보안 통제를 대신하지 않는다. 실제 동작하는 코드와 설정으로 통제한다.

### 2. 보안 코딩

최신 OWASP Top 10 및 OWASP ASVS를 보안 점검의 기준으로 삼는다. 적용 가능한 항목은 기능과 위험도에 맞춰 확인한다.

- **인증·인가:** 모든 민감한 기능과 객체 접근에서 서버 측 권한을 검사한다. 기본 거부 원칙과 최소 권한을 적용하고, 사용자 간 데이터 접근을 분리한다. 인증·세션 토큰은 안전하게 발급·저장·폐기하며, 세션 만료와 재인증을 고려한다.
- **입력·출력:** SQL은 매개변수화된 쿼리/ORM을 사용하고, 셸 실행은 피한다. 불가피한 경우 인자 배열과 허용 목록을 사용한다. HTML, URL, JSON 등 출력 문맥에 맞게 인코딩하고, 업로드 파일의 형식·크기·이름·저장 위치를 검증한다.
- **웹 보안:** CSRF, XSS, SSRF, 경로 탐색, 오픈 리다이렉트, 요청 위조, 대량 할당, 속도 제한 및 서비스 거부 위험을 기능에 맞게 점검한다. CORS, CSP, 쿠키 속성, 보안 헤더는 최소 허용으로 설정한다.
- **암호화와 비밀정보:** 검증된 표준 라이브러리와 현대적인 알고리즘을 사용한다. 자체 암호화 알고리즘을 만들지 않는다. 비밀번호는 전용 비밀번호 해시 알고리즘으로 저장하고, 키·토큰·비밀번호는 코드, 테스트 fixture, 로그, 문서에 넣지 않는다. 비밀정보는 환경 변수 또는 승인된 비밀 저장소에서 주입하고 저장소에 커밋하지 않는다.
- **오류·로그:** 사용자에게 내부 경로, 쿼리, 스택 추적, 비밀정보를 노출하지 않는다. 보안 이벤트는 조사 가능한 수준으로 기록하되 개인정보·인증정보·토큰을 기록하지 않는다. 실패 시 안전하게 거부하고 예외를 삼키지 않는다.
- **의존성·공급망:** 꼭 필요한 의존성만 추가하고 유지보수 상태와 알려진 취약점을 확인한다. 버전은 재현 가능하게 잠그고, 출처가 불분명한 패키지·스크립트를 실행하지 않는다. 빌드·배포 산출물과 업데이트 경로의 무결성을 고려한다.
- **설정·운영:** 디버그 모드와 개발용 자격증명은 운영 환경에서 비활성화한다. 기본 설정은 안전하게 두고, 필요한 권한만 부여한다. 보안 관련 설정 변경은 영향과 운영 환경 차이를 설명한다.

### 3. 개인정보 보호법 및 개인정보 보호

개인정보를 처리하는 기능은 대한민국 「개인정보 보호법」, 시행령, 관련 고시와 개인정보보호위원회 지침의 **현재 시행 내용**에 맞춰 설계한다. 법적 적용 여부나 처리 근거가 불명확하면 준수를 단정하지 말고 담당자 확인이 필요한 사항으로 표시한다.

- 목적 달성에 필요한 최소한의 개인정보만 수집·이용한다. 필수/선택 항목, 처리 목적, 법적 근거, 보유 기간과 파기 시점을 명확히 한다. 목적 외 이용·제공은 금지한다.
- 동의가 필요한 경우 동의 전 수집·처리를 진행하지 않는다. 동의는 목적과 항목별로 구분하고 철회·거부 절차를 고려한다. 동의만을 일률적인 처리 근거로 가정하지 않는다.
- 개인정보 필드와 흐름을 설계 단계에서 식별하고, 화면·API·DB·로그·백업·분석·외부 서비스까지 흐름을 추적한다. 개발과 테스트에는 실제 개인정보 대신 합성 데이터를 사용한다.
- 접근 권한을 최소화하고, 전송·저장 중 보호가 필요한 개인정보와 인증정보를 암호화하거나 법령·고시에서 요구하는 보호조치를 구현한다. 키는 데이터와 분리해 관리한다.
- 개인정보 조회·변경·다운로드 등 중요 행위의 접근기록을 남기고 위변조와 무단 열람을 방지한다. 로그에는 주민등록번호, 비밀번호, 인증 토큰 등 민감한 값을 남기지 않는다.
- 보유기간이 끝나거나 처리 목적이 달성되면 복구할 수 없도록 파기한다. 백업·캐시·검색 인덱스·로그 등 복제본의 삭제 정책도 확인한다.
- 외부 처리자, 분석 도구, 클라우드, 국외 이전 또는 제3자 제공이 포함되면 목적·항목·보유기간·위탁/이전 관계와 필요한 고지·계약·보호조치를 점검한다. 근거 없이 외부 서비스로 개인정보를 전송하지 않는다.
- 정보주체의 열람·정정·삭제·처리정지 등 권리행사를 지원할 수 있도록 관련 데이터 구조와 절차를 고려한다.
- 고유식별정보, 민감정보, 아동 개인정보, 생체정보 등 고위험 처리는 별도 법적 요건과 강화된 보호조치를 확인하고, 필요 시 개인정보 보호책임자/법무 담당자의 검토를 요청한다.
- 개인정보는 절대 저장하지 않는다.

### 4. 소스 및 개발 산출물 외부 노출 금지

- 이 저장소의 소스 코드, 설계·구성 정보, 문서, 데이터, 자격증명 및 개발 산출물은 비공개로 취급한다. 사용자의 명시적인 승인과 조직의 정책상 허용이 없는 한 외부에 공개하거나 전송하지 않는다.
- 코드·로그·설정·문서·개인정보를 외부 AI 서비스, 웹사이트, 이슈 트래커, 채팅, 코드 분석/변환 서비스, 공개 저장소 또는 외부 저장공간에 붙여넣거나 업로드하지 않는다. 외부 서비스 호출이나 연동이 기존 코드에 있더라도 전송되는 정보와 목적을 확인하고 최소화한다.
- 저장소를 공개 저장소로 전환하거나, 소스·빌드 산출물·스크린샷·로그를 공개 게시하거나, 외부 저장소/서비스로 푸시·업로드하는 작업은 수행하지 않는다. 이런 요청이 작업에 포함되어 있으면 해당 공개 동작 전에는 사용자 승인을 받는다.
- 예시, 테스트, 오류 보고, 문서화 과정에서도 실제 소스나 내부 정보를 불필요하게 복사·노출하지 않는다. 외부에 전달해야 하는 경우에는 승인 여부를 확인하고 비밀정보와 개인정보를 제거한다.
- 이 지침은 개발된 소스의 기밀성을 보호하기 위한 것이다. 저장소 접근 권한, 비밀정보 관리, 백업 및 배포 설정도 비공개 원칙에 맞게 유지한다.

### 5. 하드코딩 금지 및 설정 관리

- 환경별로 달라지는 URL, 호스트, 포트, 경로, 기능 플래그, 제한값, 타임아웃, 외부 서비스 설정, 자격증명을 코드에 직접 박아 넣지 않는다. 설정 파일·환경 변수·비밀 저장소 등 프로젝트의 표준 설정 방식을 사용한다.
- 비밀정보(키, 토큰, 비밀번호, 인증서)는 어떤 경우에도 소스·예제 설정·로그·커밋에 넣지 않는다. 예제에는 안전한 placeholder만 사용한다.
- 도메인 규칙상 고정된 값은 이름 있는 상수나 중앙 설정으로 정의하고, 의미·단위·변경 이유를 분명히 한다. 단순히 모든 리터럴을 설정화하지 말고 실제 변경 가능성이 있는 값과 보안 경계 값을 우선 분리한다.
- 설정 누락이나 형식 오류는 시작 시 명확하게 실패시킨다. 안전하지 않은 기본값으로 조용히 대체하지 않는다.

### 6. 구현 전후 작업 절차

1. 저장소 지침, 관련 코드, 의존성, 실행 방법, 기존 테스트와 변경 영향 범위를 확인한다.
2. 요구사항과 입력·권한·개인정보 흐름·실패 상황을 정리한다. 보안이나 개인정보 위험이 큰 변경은 위협과 완화 방법을 먼저 확인한다.
3. 최소 범위로 구현하고, 기존 스타일과 호환성을 유지한다. 데이터베이스·API·권한 변경은 마이그레이션과 하위 호환성을 고려한다.
4. 완료 후 반드시 검증한다. 프로젝트에서 제공하는 포맷/린트, 타입 검사, 빌드 및 관련 테스트를 실행하고 결과를 확인한다. 테스트가 없으면 핵심 로직과 실패·권한·경계 조건을 검증할 수 있는 테스트를 추가한다.
5. 보안 관련 변경은 가능한 경우 정적 분석, 의존성 취약점 검사, 시크릿 탐지, 권한·입력값·오류 처리 검토를 실행한다. 자동화 도구가 없으면 해당 항목을 코드 수준에서 점검한다.
6. 테스트를 실행할 수 없거나 실패하면 숨기지 말고, 실행하지 못한 이유·실패 내용·남은 위험을 최종 보고에 적는다. 검증하지 않은 코드를 완료됐다고 표현하지 않는다.
7. 최종 보고에는 변경 요약, 실행한 검증과 결과, 미실행 항목/제약, 개인정보·보안 관련 주의점을 간결하게 기록한다.

### 7. 테스트 작성 기준

- 새 기능에는 정상 동작뿐 아니라 잘못된 입력, 경계값, 권한 없는 접근, 예외·시간 초과 등 실패 조건을 포함한다.
- 권한 검사는 허용/거부 양쪽을 테스트하고, 서로 다른 사용자 간 데이터 격리를 검증한다.
- 개인정보 기능은 최소 수집, 마스킹/비노출, 보유기간·파기, 권리행사 및 로그에 민감정보가 섞이지 않는지 검증한다.
- 테스트는 외부 실서비스나 실제 개인정보에 의존하지 않는다. 시간·네트워크·외부 시스템은 가능하면 격리하거나 통제한다.
- 회귀 테스트를 추가해 수정한 취약점이나 버그가 다시 발생하지 않도록 한다.
